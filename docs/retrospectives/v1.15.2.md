## 1. Acceptance criteria — were they checkable, and were they checked?

**Both issues' criteria were checkable and both were checked — and in one case the gate, not the
author, is what made that true.**

- **#443's nine criteria are the best-written in either window.** Each is a *falsifiable* statement
  with the command that settles it, and one of them exists purely to falsify the others: *"Both
  browser assertions are demonstrated to **fail** against the pre-fix stylesheet"* — ticked with
  `reverted, rebuilt, re-ran: 2 failed, 2 passed`, the error naming `"text": "Hire me" … "ratio":
  1`. A contrast assertion is the archetypal check that passes vacuously (an empty selector match
  yields an empty offender list), and the criterion that would catch that was written into the
  issue rather than left to review.
- **…but #444's body asserted the criteria were ticked before they were, and the merge gate caught
  it.** Recorded by the next PR's verdict in as many words: *"(Stated explicitly because a false
  version of this sentence in PR #444's body is what the merge gate caught last time.)"*
  `pre-merge-gate.sh` refuses a merge whose `Closes #NN` points at an issue with unticked criteria,
  so the refusal is what turned the claim true. **All nine are ticked now**, each with its command.
  This is the v1.15.0 §1 finding recurring — the author leaving the ticking to a gate — with the
  difference that here the PR body *claimed* it was already done. That is the class-F shape landing
  on the AC surface, and the mechanical backstop is the only reason it cost nothing.
- **#417's four criteria are ticked with the command behind each**, verified by the reviewer
  reading the issue after the edit rather than trusting the PR body — stated explicitly in the
  verdict because of the #444 incident one PR earlier.
- **No `Closes` against an unmet AC. Zero — fifth release running.**
- **One criterion recorded a limitation instead of quietly passing.** #443's ninth AC
  (*"No real employment history enters the public repo"*) is ticked and carries its own caveat:
  *"NOTE: the guard passed **before** the scrub too, because those strings are not on its exclude
  list"*. A ticked box that names the reason it is weaker than it looks is worth more than an
  untickable one; the action it generated is in §6.

**Action shape:** nothing to `issue-author` — these criteria are the standard other issues should
be held to. The ticking gap is an author-side habit with a working mechanical backstop, exactly as
v1.15.0 concluded; a third instance would change that judgement.

   for the step.
2. **The retrospective step was skipped here too** — this document and v1.15.1's were both written

   (`bump_version.sh` now reports whether the previous release's retrospective exists). **The same

**A third, smaller one, measured on the board:** **#443 was never a GitHub Project 3 item at all**,

## 3. Code quality — the classes

**Three PRs is not a sample, so this section reports instances rather than rates.**

**Class F in review — 0.** The same caveat as v1.15.1 §3 applies without change and is not restated
here: all three verdicts were written by the PR's own author, so this cell counts what a session
caught re-reading itself. See [v1.15.1 §3](v1.15.1.md) for the control that shows what self-review
misses.

**Class G ("a check that cannot fail") — 0, and both PRs went looking for it.** This is the
substantive good news of the window and it is worth quoting, because both PRs add a *check* and
either could have shipped a decorative one:

- **#444** added two Playwright contrast assertions — the exact shape that passes when the selector
  matches nothing. Ruled out by observation: revert the fix, rebuild, re-run → **2 failed, 2
  passed**, with the offending element named. The guard reproduced the reported symptom.
- **#445** added a *test gate* (the importer suite, into the pre-push leg + CI + `verify_all.sh`),
  which is the archetype: a leg that is selected but never executes, or that skips when its
  interpreter is missing, passes every check anyone would think to run and gates nothing. Ruled out
  end-to-end: a failing case was appended to `importer/tests/test_importer.py`, the hook driven for
  real → `1 failed, 15 passed`, `"permissionDecision":"deny"`, and — the part that makes it
  attributable — **the log's only `✗` names the importer leg**, not one of the dozen other checks in
  the same block. The silent-skip half is handled in code, not a comment: the block prefers
  `backend/venv/bin/python`, falls back to `python3`, and **fails with the command to run** if
  neither can import pytest.

**Class N (a new control breaks on first real material) — 1, and the handling is the lesson.**
Mapping `importer/**` in `prepush-select-lib.sh` silently invalidated six existing fixtures that
had been using `importer/ledger.py` as their *unmapped* path — three of them the ALL-round stub
cases that pin "the gate never passes `--mutations` to a hook self-test locally", which is a budget
guarantee the owner set explicitly. They failed as `got=""`, the ambiguous shape: an assertion that
observes *nothing* looks identical whether the mechanism moved or the harness broke. **The author
stashed the three hook files and re-ran the baseline clean before touching anything** — attributing
the breakage to the change rather than assuming it. Final contract: `pre-push-tests.test.sh
--mutations` **49 killed, 0 survived, 0 invalid**, including the new
`importer paths stop selecting the importer suite (#417)` mutant, which neuters the rule to *select
nothing* rather than deleting it (selecting nothing passes every "X must not be selected" case and
would otherwise be invisible).

**Class T — 0.** The class v1.15.1 defined (a PR's own argument not applied to the second instance
in the same file) has no instance here. With one window of data and a 3-PR corpus this is
information about the corpus, not about the class.

**Stale-base blockers — 0**, fourth release running; all three PRs were rebased and the verdicts
are delta-confirms at the rebased heads (`7f2fa681`, `d765cf70`, `c26cd652`).

**One defect this window found in a guard, rather than in a PR** — the `check_no_pii.sh` gap, raised
by #444's verdict and deferred here by name. See §6.

**3 of 3 carry the rule-13 non-independence disclosure** — part of the 9-of-9 across both windows
measured in [v1.15.1 §4](v1.15.1.md), which is where the measurement and its near-miss are
recorded. #446's disclosure is the most precise of the nine and deserves quoting, because it names
a compounding that the rule's text does not: the release-PR verdict was written by the session that
*"authored this release branch, ran the bump, and authored and self-reviewed **both PRs the release

release PR whose contents were themselves self-reviewed is a second-order case, and the only reason
a reader can see it is that the verdict said so.

**What the reviews did that is worth keeping, on a window where reviewer and author were one:**

- **They re-derived rather than re-read.** #445's verdict did not accept "the inline CI step was
  tried and reverted" as a reason — it checked *why* (`version-consistency` has only
  `actions/checkout@v7`, no `setup-python`, and runners do not ship `pytest`, so the step would have
  failed as an infrastructure error or been made green with `|| true`; it is also on the prod-deploy
  critical path with four build jobs `needs:`-ing it). "I tried it the other way" is exactly the
  kind of claim that is usually decoration, and this one was not.
- **They checked blast radius on a change that makes a gate CHEAPER.** `importer/**` used to buy the
  full round and now buys `importer pii`. That is only safe if an importer change cannot break
  anything outside `importer/` — verified, not assumed:
  `grep -rn '^\s*\(from\|import\)\s\+importer' backend/ frontend/ scripts/` returns nothing, and the
  `pii` leg is never selectable away.
- **They refused to bank a passing number without the measurement that proves it executed.** #444's
  E2E evidence is `89 passed` — *"the previous 87 plus exactly the two tests this PR adds, which is
  the measurement that the new specs actually executed in CI rather than being silently skipped"*.
  That arithmetic is the difference between a green tier and a green tier that ran your code.
- **The release verdict refused the contents, not just the rotation.** #446 re-checked both PRs the
  release carries before approving the bump, and stated what the verdict does *not* cover (rule 8 is
  not satisfied by the merge; the host must verifiably serve 1.15.2, read from the rollout log and a
  live probe, never from the job status — lessons §7).

**And one thing no review in this window did: catch something the author had not already caught.**
Zero of the three verdicts raised a blocker or a major. On a 3-PR window that is unremarkable in
isolation; across nine PRs and nine solo verdicts it is the pattern
[v1.15.1 §4](v1.15.1.md) analyses. The two findings this release produced — the merge gate's
AC refusal on #444 (§1) and the `check_no_pii.sh` gap (§6) — came from a **hook** and from the

**Most of this window's findings are answered by the v1.15.1 retrospective's changes, and are

**A. GitHub Project 3 — #443 added to the board; #417 and #443 back-filled.** `Review rounds` = 1
each (thread-derived, from the single pre-merge verdict on each PR), `Agent` = `main-orchestrator`
(the window ran solo, by owner directive), `Model` = `opus-5`, `Release` = `v1.15.2

column headed "Tokens" is the defect that retirement exists to stop.

**B. `check_no_pii.sh`'s coverage gap — FILED, not patched, and the reason is stated.** #444's
verdict raised it and deferred it here by name: *"`check_no_pii.sh` passed **before** the fixtures
were scrubbed of real employer names, because those particular strings are not on its exclude list.
The scrub happened by intent, not because the guard caught it."* The guard's scope is the former
owner's own identifiers (name, email, LinkedIn handle, GA id) plus the de-branding contract — real
*third-party* employer names are outside it by design, and whether they should be inside is a scope
decision with a live tension: this product is a portfolio template, and a real deployment's career
history legitimately contains real employer names. Widening a guard that **fails closed** on a
judgement call nobody has made would turn a correct commit into a blocked push. Filed as **#454**
with the incident attached and the three options costed, so the decision is made once and recorded.
(Tracked with the second deferral from [v1.15.1 §6 G](v1.15.1.md) — the merge gate's bypass
PR-comment that silently fails, filed as **#453**.)

**C. Rule 8's security step — no new control.** Named deliberately, because the hard rule says a
retrospective that produces no change on a finding must say why. v1.15.2 skipped the release-time
security check, and the cheapest mechanical fix (report it at the cut, beside the release-queue and
retrospective lines) is **rejected for now**: the check is a *triage*, not a file test, so
`bump_version.sh` can only ever assert that someone posted something — a check that cannot fail, on
a release surface, which is the class this series counts. The correct enforcement point is the
release PR's own checklist and `release-manager`'s step order, both of which already say it. Two
consecutive misses would change this judgement; one miss on a 1.6-hour patch release does not
justify shipping a decorative gate.

## 8. Prediction for the next release

**The standing prediction is [v1.15.1 §8](v1.15.1.md)'s six clauses, carried forward unchanged** —
they were written for the next window and this release does not get to rewrite them. Two additions
this window's own evidence justifies, and no more:

7. **A release-time security check is posted on every release PR before its merge**, naming the
   three feeds and proving at least one uploaded an analysis at that release's head — the shape
   v1.15.1 used on #441. Scored from the PR thread at `mergedAt`; a retrospective count of open
   alerts does **not** satisfy it, for the same reason a back-filled verdict does not satisfy rule
   13.
8. **Every issue a release closes is a Project 3 item carrying its `release:vX.Y.Z` label before the
   cut.** #443 was neither. Scored at the cut, from the label queue the release-queue gate already
   queries — which is also the falsifier: **the gate reports `empty (checked)` for an issue that was
   never labelled**, so clause 4 passing and clause 8 failing are compatible, and clause 8 is what
   closes that hole.

**Falsifiers for the two new clauses.** (f) Clause 7 can be satisfied by pasting a template with
three zeros in it; the check is only real if it names the analyses uploaded at that head, so score
it against the *evidence of liveness*, not the zeros. (g) Clause 8 goes to "pass" for free on a
release that closes no issues at all — state the issue count beside it, and score it n/a rather
than pass when that count is zero.
