## 1. Acceptance criteria — were they checkable, and were they checked?

**The criteria themselves were good. The ticking was not, and it was left to the reviewer.**

- **#431: all 15 ACs met, all 15 unticked at review time.** The round-1 verdict had to spend a
  finding on it — *"⚠️ Required before merge, independent of this verdict: all 15 boxes on #431
  are `- [ ]` (0 ticked). `pre-merge-gate.sh` refuses a merge whose `Closes #NN` points at an
  issue with unticked criteria, so tick them (they **are** met — the table above is my
  verification) rather than reaching for `PR_MERGE_GATE=0`."* The reviewer then verified all
  fifteen independently and published a criterion-by-criterion table. So the gate worked, the
  criteria were genuinely checkable, and the cost was a reviewer round spent on bookkeeping the
  author could have done. This is the inverse of the v1.14.3 defect (ticked without evidence) and
  cheaper, but it is still a round.
- **#264 under-claimed deliberately, and that is the model.** The PR carries `Refs #264`, not
  `Closes`, with the gap named precisely: AC1/AC7 need the recording widget and admin player plus
  their specs, and **AC5's latency figure was measured on an 8-core arm64 laptop rather than the
  small-VPS class the criterion names**. Naming the wrong hardware class rather than quietly
  ticking a met-looking number is exactly what §1 has been asking for since v1.12.0. #264 stays
  open and moved to `release:v1.15.1`.
- **No `Closes` against an unmet AC. Zero.** Third release running.
- **One AC was unmeasurable as written and was closed honestly by the reviewer rather than the
  author:** #424's AC2 (*"applying `run-e2e` still triggers the E2E lane"*) had never been
  exercised — the only label event since the split was `tech-debt`. The round-2 verdict said so
  (*"AC2 is half-unmeasured"*) and the author then fired the real label to close it, with the run
  id. A criterion that needs a live event to prove it needs someone to fire the event.

**Action shape:** nothing goes to `issue-author` — the criteria were well written. The ticking
gap is an author-side habit, and it already has a mechanical backstop (`pre-merge-gate.sh` refuses
the merge), so the cheapest fix is the one already in place. No change.

## 2. Issue quality — and the one the OWNER had to catch

**This section's finding is about me, not about the issues.**

The release was assembled from what `CHANGELOG.md [Unreleased]` happened to contain. **The
`release:v1.15.0` label queue was never queried** — not once, at any point before the tag. The
owner caught it after the fact: *"is see more issues for 1.15.0 in the backlog, why they are
ignored?"* Measured on the challenge, **#70, #265 and #386 were all still labelled
`release:v1.15.0` and open** when the release PR was cut.

What makes this worth a change rather than an apology: **the rule already existed and was already
specific.** `release-manager.md` step 1 has said *"Never cut the release PR while issues planned
under `release:vX.Y.Z` are still open unless the owner explicitly de-scopes them, named one by
one"* since the v1.14.3 revert, which cost two PRs, a cancelled deploy and that window's only
rule-13 violation. The paragraph did not fail — it was **never executed**. A rule that lives only
in prose depends on someone remembering to run it, and under a solo, keep-shipping directive that
is precisely what gets skipped. Lessons §30: assert at the layer that can enforce. Hence §6
change B, which puts the query inside `bump_version.sh` — the command that *is* the release cut.

The triage the challenge forced was also substantively right, and worth recording:

- **#70 is far more shipped than its label implied.** The interviews backend and admin UI landed
  in **v1.13.0**; only public self-booking remains. The label had been carrying a mostly-done
  issue forward for two releases.
- **#265 and #386 should never have had a release label at all** — a roadmap tracker and a KPI
  issue. Both now carry none, per this directory's own convention (*"a tracking issue gets no
  release bucket"*), which had not been applied to them.
- A superseded `feat/70-interview-calendar` branch was deleted after proving its only unique
  content was a retired brand string (tip `af579dc9` recorded first).

Grounding quality on the issues that *were* worked: good. No `path:line` citation went stale, no
implementer had to re-research a diagnosis. #431's issue survived contact with the code
completely — the only thing it got wrong was a third-party claim (§3), which no amount of
in-repo grounding could have caught.

## 4. Review actions — and the uncomfortable thing about the 50%

**Round-1 approvals hit 50% (3/6), the series best by a wide margin (previous: 29%). The
confound has to be published with it: the two PRs approved in round 1 by the main session are the
two that had no independent reviewer.**

| | PRs | Round-1 approvals |
|---|---|---|
| Reviewed by a `pr-reviewer` agent | #429, #430, #433, #435 | **1 of 4** (#435) |
| Reviewed by the main session (solo directive) | #434, #436 | **2 of 2** |

**#434 was the largest PR of the release — 24 files, +1983 lines, a new public endpoint, a new
Alembic migration and a local Whisper dependency — and it was approved in one round by the same
session that had just rebased it and resolved two of its conflicts.** The verdict says so in its
own first paragraph, and the review was substantive (it verified the duration cap is re-checked
against decoded audio, that the admin route is behind `get_current_admin_user`, that the suite
forbids loading a real Whisper model, that it ships OFF in both compose files). It is still not
an arm's-length look, and the 50% cell must never be quoted without this table.

**Nothing downstream can tell the difference.** Reviewer and author share one GitHub identity
here, so `audit_no_verdict_merges.sh` counts a self-review, the trend table counts its round, and
`pre-merge-gate.sh` passes it. The only party that knows is the session writing the verdict —
which is why §6 change D makes the disclosure a rule rather than the improvisation it was this
window. All four solo verdicts (#433 r3, #434, #436, plus the #437 verdict outside the window)
carried it voluntarily; the next session should not have to reinvent that.

**What the agent reviewers caught that authors missed**, and what repeated:

- **Third-party claims, twice, in different shapes** (#433's vendor list; #429's undocumented
  filter). Both are "a fact about something outside this repo, asserted without asking it".
- **A permanent surface disagreeing with its own PR body**, three times (#430 findings 3 and 4;
  #433 finding 7). The PR body was honest in every case; the CHANGELOG, the wiki page, and
  `config.py` were the ones that lied, because a correction was applied to some surfaces and not
  all. This is the v1.14.1 four-copies mechanism at smaller scale, and the single-source rule
  does not reach `config.py` comments or docstrings.
- **Reviewers verified by RUNNING, consistently.** #433's round 1 killed **16 mutants** by hand,
  each attributed to a named test, and re-measured coverage (`1239 passed`, `4104 statements`,
  `0 missed`) rather than quoting the PR. #430's rounds re-ran the v1.14.2 restatement predicate
  across both articles and published the before/after counts (14 → 9 → 8). #435 ran
  `caddy validate` in a container and the 27-case apply contract. **No review round in this
  window found nothing** — every negative verdict reproduced a defect, which is the v1.13.0
  counter-evidence to a "churn" reading, again.
- **One review found a defect the author then improved on**: #433's reviewer suggested splitting
  the workflow; the author split it *and* measured why the cheaper alternative fails *and*
  proved the fix with real label events. That is the loop working.

## 6. The changes

Enforcement order, cheapest thing that actually prevents recurrence.

**A. NEW `scripts/retro_metrics.sh` (tooling) — the retrospective's figures become executable.**
Class F has been top or joint-top for five consecutive releases and its instances are
overwhelmingly hand-counted figures **in these documents** (5 of this window's 7). Charter prose
has not moved it. The script encodes the three bounding rules that have each cost a release —
bound on the release PR's `mergedAt` (note 12), normalise to UTC (note 11), replay every verdict
at `mergedAt` (note 13) — plus the anchored filter, and prints corpus, median files/PR, canonical
verdicts, mean rounds, round-1 approvals and rework share. It carries the §67 `BASH_SOURCE` guard
and states in its own header what it cannot do (decide anything; distinguish a self-review).
Wired into `/retro` step 2 and the `release-retro` skill's Inputs section as the first thing the
retro runs. **It produced every cell of this document's headline table**; what it cannot produce is
listed in the preamble, and the script's own header states its limits (it decides nothing, and it
cannot tell a self-review from an independent one).

**B. `bump_version.sh` gains a release-queue gate — the §2 finding, made mechanical.** Before the
version moves, it asks GitHub for open issues labelled `release:v<new version>` and **refuses the
cut** if any exist, printing them. Fails **open** when `gh` is missing, unauthenticated or
offline — and says `UNVERIFIED (not empty; unchecked)` so "I could not check" can never read as
"the queue is empty". Deliberate owner de-scopes bypass it with a **named** `RELEASE_QUEUE_GATE=0`,
visible in history like `PR_MERGE_GATE=0`. Run against the live repo it reproduces the miss
exactly: cutting 1.15.1 today is refused, naming #425, #339, #264 and #70.
**Proof it can fail (§69):** four new cases in `test-bump-version.sh` driven by a stubbed `gh` on
`PATH` — never the network — covering block / pass-and-say-it-checked / fail-open-as-UNVERIFIED /
bypass-works; **23 passed, 0 failed**. Mutation-checked: neutering the gate (`if false`) kills 3
of the 4, and inverting the emptiness test kills 2 — the surviving case in each is the bypass
case, which a removed gate also satisfies, and that is stated rather than counted as a kill.

**C. `docs/retrospectives/README.md` — the telemetry columns retired (note 21), and the trend row
added.** Fourth strike on a binary clause; see §5. Historical cells preserved.

**D. `CLAUDE.md` rule 13 — a non-independent verdict must disclose itself.** 3 of 6 PRs merged on
a main-session verdict this window, including the largest. Nothing downstream can detect that, so
the disclosure has to be written by the only party that knows; the rule names what to state (who
produced it, and what else that session did to the branch) and says plainly that a solo verdict is
still a real gate and still better than merging unreviewed — it is simply not what rule 13 asks
for, and the record must not imply otherwise.

**E. `lessons-learned` §39 EXTENDED, not a new §77.** The incident: a gated `gh pr merge` chained
behind the `cat > verdict.md` heredoc that produced its own input. The merge gate denied the
chain, so per §26 nothing ran — the verdict was never posted **and the file never existed** — and
the retry failed with `no such file or directory`, which reads like a filesystem bug three
commands away from the cause. §39 already said "never chain state-changing steps ahead of a gated
command"; the new corollary is that **the artefact a gated command consumes must exist before you
compose it**. Adding a §77 restating §39 would be the dilution this skill warns about, so the
lesson went where a reader will already be looking.

**F. `CLAUDE.md` rule 12 — stale reference corrected.** The parenthetical named
`pr-evidence.yml` as carrying both tiers; #433 split the browser tier into
`pr-evidence-e2e.yml` and correctly declined to edit project configuration on an agent's request,
handing it over instead. Applied here with the reason, closing the one item that PR left open.

**Considered and NOT changed:** `issue-author` (the criteria were well written — §1);
`pr-reviewer` (it caught every class-F instance, verified by running, and left no round empty —
the author side is where the defects originate); the plugin set (no new evidence either way this
window; `frontend-design` stays dropped, and #434's voice work was backend-only so it triggers
nothing). Adding a charter paragraph about hand-counted figures was **rejected** in favour of
change A — five releases of paragraphs are the evidence that paragraphs do not work here.
