## 1. Acceptance criteria — and the release's worst finding

Criteria themselves held up: the reviewer verified rather than read ticks on every reviewed PR,
and #406's four rounds each closed with a per-criterion table. **No `Closes` was posted against
an unticked criterion**, and #407 was deliberately carried as `Refs` with a manual close-the-loop
precisely because the merge gate would have refused a `Closes`.

**But rule 13 — the criterion that governs every PR — failed six times.**

| PR | Verdicts at `mergedAt` | Newest pre-merge verdict | Merged |
|---|---|---|---|
| #394 | **0** | — | 14:23:19Z |
| #395 | **0** | — | 14:23:31Z |
| #396 | **0** | — | 14:23:43Z |
| #397 | **0** | — | 14:32:58Z |
| #403 | **0** | — | 14:41:56Z |
| #402 | 1 | **⛔ REQUEST CHANGES — round 1** | 14:36:08Z |

Five PRs merged with **no verdict at all**; #402 merged **against a standing REQUEST CHANGES**,
with a fix commit at 13:56:25Z that no one re-reviewed. All six merged inside an **18-minute
window** (14:23–14:41Z) during release assembly. That is **6 of 14 PRs — 43%** — against 1 of 17
at v1.14.1 and 1 of 11 at v1.14.0.

**Three facts establish what happened, and one of them is new evidence the repo could not
previously obtain:**

1. **The gate was never reached.** `pre-merge-gate.sh`'s bypass trace (#392, shipped this cycle
   in #399) writes `$HOME/.claude/merge-gate-bypass.log` and posts a `⚠️ MERGE-GATE BYPASS`
   comment on every `PR_MERGE_GATE=0` merge. **The log does not exist and no such comment exists
   on any of the 14 PRs.** So these were not authorized bypasses — they were merges that never
   passed through the CLI at all. v1.14.1 had to report provenance as *unmeasurable*; the empty
   bypass log now lets us say something stronger and true: **not a bypass, a different path.**
2. **The detector could not have fired in time.** `.github/workflows/verdict-audit.yml`'s cron is
   `17 6 * * 1` — **Mondays 06:17 UTC**. 2026-09-14 *was* a Monday, so the week's only scheduled
   run happened **eight hours before** the first violation; the next is 2026-09-21. The single run
   in the window (`34828944837`, 09:37Z, `workflow_dispatch`) was the post-merge smoke test of
   #399 itself and was green because nothing was dirty yet. A weekly alarm has a detection
   latency of up to **seven days**; this release lived and died inside one.
3. **The detector cannot fire *at all* now, because the evidence was repaired.** At 15:45:11–
   15:45:30Z all six PRs received `APPROVE — retrospective review (round 1)`. Re-run today:

   ```
   $ bash scripts/audit_no_verdict_merges.sh --since 2026-09-14T00:00:00Z --limit 100
   audit: all 14 merged PR(s) in the window carry a canonical verdict     # exit 0
   ```

   The auditor tests **presence**, not **ordering**. A verdict back-filled an hour after the merge
   satisfies it exactly as well as a review that gated the merge. The control built to catch
   #321 and #355 reports this window clean.

The retrospective verdicts are honest documents — each names the merged-result evidence it
rests on, and #402's correctly re-derives the foreign-repo polarity. They are the right
fix-forward. They are not a substitute for a gate, and the metric must not treat them as one.

**Two further observations, since all six arrived in 19 seconds:** this was **one batched review
run covering six PRs** — the practice the owner banned mid-v1.14.1 after it cost 425k tokens
across four runs — and four of the six were Dependabot PRs, the same flow shape as #321. Rule 13
says "no carve-outs… dependency bumps" in terms; the dependency tranche is nevertheless where it
breaks, twice now.

## 3. Code quality — blockers clustered by class

**Predicate, stated because it changes the answer** (same as v1.14.1): a PR is counted in a class
when a finding of that class was raised at **blocker or major** level in a posted verdict. Nits
and minors are excluded. Each count was re-derived from the verdict bodies for this record.

| Class | What it is | PRs affected | Count |
|---|---|---|---|
| **F — claim not measured / overstated** | a number or statement in a permanent file contradicted by the thing it describes | #388 #389 #400 #402 #406 | **22** |
| **G — a check that cannot fail** | fake-green: an inert sweep, an unkillable mutation, an untested live path, a case pinning the wrong thing | #388 #390 #399 #400 | **8** |
| **N — a new control's first contact with real material** | a gate that passed its own suite and broke on the first real input | #399 #400 #406 ×2 | **4** |
| **B — stale / conflicting base** | branch behind or conflicting with `main` at review time | — | **0** |
| **C — `[Unreleased]` collision** | duplicate heading or entry in the merged result | — | **0** |

**Classes B and C went to zero, and that is the release's clearest engineering win.** From 5 and
7 respectively at v1.14.1 to none. Two reviewers stated the branch state explicitly and unprompted
(#389 r1: *"Base is current (0 behind `origin/main`, `MERGEABLE`) … I did not spend this round on
stale base"*; #406 r3: *"Base: `fcb4c20` · `MERGEABLE` · … = **0**. Not stale."*). Both #391 (the
merged-result CHANGELOG lint) and #375 (the stale-base deny) shipped, so the ✅ is earned rather
than lucky — v1.14.1's own falsifier for this clause was "score it only alongside whether #391
shipped", and it did, in #398.

### Class F is 82% one PR, and that is the finding

**18 of the 22 class-F findings are on #389 — the v1.14.1 retrospective PR itself.** Its round-1
verdict opens `## Blockers` and lists thirteen, every one a published number contradicted by
measurement; rounds 2 and 3 added five more. A sample, quoted:

- *"The cost figures disagree with themselves across three files in this PR. Same window, same
  instrument, **four readings**."*
- *"`v1.14.1.md:171-216` '## 7. Changes made' lists changes that are **not made**."*
- *"'two guarded commands deny→allow' **understates the measured regression by five**."*
- *"'#373 took 8 verdicts' is 7 — one canonical match is an AUTHOR comment."*
- *"Class F = 2 is an undercount, and it is the cell that **scores the standing prediction ✅**."*

The remaining four are ordinary: #400 round-3 (*"killed by two independent cases on each
platform" — true on Linux, not macOS*), #400 round-4 (*mutation numbers stated against the OLD
34-case suite*), #402 (*the committed causal explanation is contradicted by measurement*), and
#406 round-1 (*the PR body's push-gate evidence is not reproducible*).

**The mechanism is structural, not carelessness.** The v1.14.1 retrospective published the same
figures into **four** places: `v1.14.1.md`, `README.md`'s trend table,
`docs/wiki/team-and-process.md` and `docs/wiki/delivery-statistics.md`. Measured on `main` today,
those two wiki articles still restate this release series' figures **24 times** (16 and 8
occurrences of `2.41` / `2,600,168` / `153k` / `5 of 17`). Every correction in review therefore
had to land in up to four files, and #389's rounds 2 and 3 exist precisely because a correction
landed in three of four (*"`delivery-statistics.md:92-94` — still **two** guarded commands"*;
*"the withdrawn 'wrong stack' claim survives"*).

Four copies of a number is four chances to be wrong and one chance to be right. **The fix is not
another instruction to check more carefully — it is to stop making copies** (§6, change A).

**And the class shipped anyway.** `README.md:395-396` and `CHANGELOG.md:212-215` publish different
numbers for the same measurement with no qualifier:

| push shape | `README.md` | `CHANGELOG.md` |
|---|---|---|
| docs-only | `11m44s → ~3s` | `11m44s → 13s` |
| backend-only | `11m44s → seconds` | `11m44s → 1m21s` |
| `projects/public/**` | `11m44s → ~15s` | `11m44s → 15s` |

Both are honest measurements of *different gates* — `git log -S` dates the CHANGELOG table to
`e203eb6a` (#388/#377, deep legs still local) and the README text to `9303b40b` (#405/#404, deep
legs moved to CI, which is why backend-only fell from 1m21s to seconds). Neither says so. This
retro's PR fixes the attribution.

### Class G rose 2 → 8, and the control for it is the one that did not ship

Every instance is a check that passed while being unable to fail: #388's `dedup` mutation no
longer matching its target and the `leg_exact` gate keeping `--mutations` out of the round; #390's
new case pinning "blank lines survive" instead of "byte-identical"; #399's auditor live path with
**no tests at all**; #400's reverse MCP sweep *"inert on GNU grep, so the category still cannot
fail where CI runs"* and its round-4 regression *"from fail-closed to silent pass"*.

**#393 — "a mutation contract for every repo-contract check", filed by the v1.14.1 retrospective
for exactly this class — is still OPEN.** Of that retro's three filed issues, #391 shipped
(#398) and #392 shipped (#399); #393 did not, and its class quadrupled. This is the direct test
of "an issue nobody lands is a finding deferred, not a finding fixed", and the answer is that the
deferred one is the one that hurt.

### Class N is new, and it cost the release PR half its rounds

Four controls broke on first contact with real material after passing their own suites:

- **#391's `check_changelog_merge.sh`** shipped at 07:40Z and false-failed the **first release
  rotation it ever saw** at 17:11Z — *"346 × `FAIL check 4: [Unreleased] line on base is LOST`…
  Measured on this head: **347** non-empty base `[Unreleased]` lines, **346 'lost' block-scoped,
  0 lost file-wide**. Nothing was dropped; the lint is wrong, not the CHANGELOG."* A release
  rotation moves every `[Unreleased]` line into a versioned heading *by design*, and block-scoped
  set semantics cannot tell "rotated" from "clobbered". The lint would have reddened **every
  future release PR**.
- **SonarCloud** was activated at 14:41Z (#403) and was structurally red on every PR from that
  moment — *"`sonarqube.yml:48-70` runs the scanner with no prior pytest/Vitest step, so the
  coverage paths … never exist"*, giving `new_coverage = 0.0` against a threshold of 80. Fixed
  in-PR (#407): gate went `ERROR / 0.0` → **`OK / 100.0`**.
- **#400's MCP sweep** was inert on GNU grep — i.e. on the platform CI runs.
- **#399's auditor** shipped its live path untested (caught in review, fixed in-PR).

The common shape: **a control is validated against fixtures its author chose, then meets material
the author did not think of — and the first real instance is a production-shaped one.** The lint
and the Sonar gate both shipped and hit first contact *in the same cycle*, and between them they
consumed **rounds 1 and 2 of the release PR**.

**A further instance appeared while this retrospective was being written, in the same lint.** It
is **not counted in the table above** — the predicate is "raised at blocker level in a posted
verdict *inside the window*", and this one was raised by the gate itself, after the tag. It is
recorded here because it is the clearest evidence in the release for what class N actually is.
The pre-push gate refused this PR:

```
FAIL check 4: [Unreleased] line on base is LOST in the merge: `- Placeholder for next release.`
```

The release-manager seeds a freshly rotated `[Unreleased]` with that literal stub
(`release-manager.md` step 4), and **the first PR after a release deletes it as it adds real
entries** — the established convention, which `git show` confirms #388 followed after v1.14.1 and
its predecessor followed after v1.14.0. The lint shipped in #398, *after* both, so this
retrospective's own PR is **the first post-release PR it has ever seen**, and it read the stub as
content loss. Left alone it would have blocked the first PR of **every** future release.

That makes three first-contact failures in one control — a release rotation (#406 round 1), the
post-release stub (here), and #400's platform inertness — each one a shape the author did not
enumerate because each is produced by the *release process* rather than by a contributor. **The
generalisable lesson is sharper than "test more": a lint over a file that an automated process
rewrites must be run against every state that process produces.** For `CHANGELOG.md` that is
exactly three — mid-cycle accumulation, the rotation, and the first entry after a rotation.
Fixed in this PR (§7 change H), with the exemption narrowed to the one literal string the release
process itself writes, a failing-first case measured against the pre-fix script, and a mutation
proving the exemption cannot go blanket.

## 4. Review actions — what review caught that authors missed

Every finding below was raised against **green CI**.

- **A lint that would have blocked every future release** (#406 r1), caught because the reviewer
  reproduced the failure locally and then measured the *right* denominator — 0 lines lost
  file-wide against 346 lost block-scoped.
- **A new deny that pre-empted a pass-through shipping in the same PR** (#406 r2): the chain deny
  sat at line 320, the foreign-repo pass-through decided at ~530, so *"`git add -A && git commit
  -m notes && git push` … is precisely how a wiki page gets updated, so this fires on the next
  wiki edit."* Measured against a real fixture repo, both polarities.
- **A hard DENY issued from a parse the hook had just declared untrustworthy** (#406 r2):
  *"a 24716-character `git commit -m '<prose containing the word push>'` — a command with **no
  push in it at all** — is DENIED."*
- **An order-awareness fix that overshot** (#406 r3): the short-circuit fired on the *first* push,
  so `git push && git commit --amend && git push --force-with-lease` — *"an ordinary fixup flow,
  not a contrived one"* — went GATE when it should DENY. The second push ships a HEAD the gate
  never examined: **the incident §65 exists to stop, still reachable in the fix for it.**
- **A guard regressed from fail-closed to silent pass** by a round-3 fix (#400 r4).

**Two reviewer behaviours are the charter working, and both are now routine rather than
exceptional.** First, **mutation as proof rather than assertion** — on #406 alone the reviewer
ran the new cases against the pre-fix code in a scratch worktree three separate times and reported
the counts (*"5 of the 8 `chain_check` cases fail"*; *"**5 of the 6** new cases go red against the
unfixed code, the 6th being the positive control"*; *"**166 passed / 1 failed** when the round-4
test file runs against `fcb4c20`'s hook"*). Second, **re-deriving the author's numbers rather than
reading them** — which is the only reason 22 class-F findings were caught at all.

**Did any round find nothing?** No. All 32 pre-merge verdicts raised at least one finding, and
the two APPROVEs that were later *retracted* (#390 round 2→ REQUEST CHANGES round 4; #400 round
2→ REQUEST CHANGES round 3) show the reviewer re-opening on further reading rather than closing
out. Rounds are not churn here; they are the gate working on material that was genuinely hard.

**The owner intervened four times, and each intervention is a measurement the agents should have
made themselves:**

| Intervention | What it corrected |
|---|---|
| *"Full gate validation must be applied only to the main branch! For simple push to the PR — formatting, compilation, something easy"* | the gate's scope |
| *"push cannot be longer as 1 minute! Never ever!"* | the push budget, now a hard constraint in CLAUDE.md rule 3 |
| *"Why the PR is not labeled? / Where is the fucking release label?"* | labels at creation (issue-flow rule 6) |
| *"Are you blind that the pipeline is red?"* | a red SonarCloud gate deferred to #407; deferral **rejected**, fixed in-PR per rule 11 |

The last one matters most for the config: the agent's instinct was to file an issue, and rule 11
already forbids that for anything the PR introduced or that is cheap to fix. The rule was right
and was not followed; the reviewer had in fact *already* said so — *"shipping it with a
permanently-red gate is exactly the normalised-red erosion the repo's own #372 note warns
about"*.

- **Stale-base rounds: 0**, from 2. The ~140k v1.14.1 spent on rounds that produced nothing but

## 7. Changes — what this PR lands, and what it files

Enforcement order applied: **hook > skill > charter > `CLAUDE.md` > command.**

### A. Single-source the numbers *(skill — the main change)*

`release-retro/SKILL.md` gains a hard rule: **the retro file and the trend table are the only
places a release figure is written. Every other document links; none restates.** Evidence: 18 of
22 class-F findings on #389, caused by four copies of every figure; 24 restatements still live in
the two wiki articles; three of #389's four round-2/3 findings are corrections that landed in
three files out of four.

Demonstrated, not just asserted: **this PR adds no v1.14.2 figure to
`docs/wiki/delivery-statistics.md` or `team-and-process.md`.** If the next retro's class-F count
does not fall, the diagnosis was wrong and should be replaced rather than repeated.

### B. Count at `mergedAt`, not at read time *(skill + conventions)*

Three measured convention defects, all of which changed a headline number this cycle:

1. **Corpus upper bound = the release PR's `mergedAt`**, not the tag commit's committer date —
   off by one second here, which dropped #406 from its own release.
2. **Replay verdicts at `mergedAt`.** A post-merge back-fill is not a round-1 approval. The naive
   filter reports 36% round-1 approvals for this window; the true figure is **0%**.
3. **The author-body hole is now closed in the convention.** v1.14.1 measured it on #373 and said
   "next retro fixes the filter"; this one states the rule (position is not authorship, *and*
   a verdict must predate the merge) and records what it changes.

### C. A new control must meet real material before it ships *(charter — `pr-reviewer`)*

Class N, 4 instances, 2 of the release PR's 4 rounds. The reviewer now asks, for any PR that adds
or modifies a gate: **what is the first real input this will see in production, and has it been
run against one?** Named triggers from this cycle: a `CHANGELOG.md` lint must be run against a
**release rotation**; a CI gate must be shown **green on a real PR**, not merely "wired"; a shell
