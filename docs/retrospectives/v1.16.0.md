## 1. Acceptance criteria — were they checkable, and were they checked?

**Two criteria were ticked against evidence that could not fail, and both were caught by the
reviewer re-measuring rather than reading.**

- **#450 (themes), AC5.** The PR ticked "the contract is pinned by a test"; the reviewer measured
  the assertion and found it passed against every mutation it was supposed to catch. The
  replacement was accepted only after **six mutants, six kills**, re-run by the reviewer at the
  PR's own head — not reported by the author.
- **#451 (projects showcase), AC6.** "Backend serves projects without leaking non-allowlisted
  fields" was ticked; a non-dict `links` bypassed the nested allowlist. Measured, not argued.

**The criteria themselves were checkable.** Across the eight issues this release closed, every AC
list is a concrete checkable list with `path:line` grounding (#93's is the clearest example: six
criteria, each naming the file it is satisfied in). No criterion in this window was unachievable,
and no `Closes #NN` landed against an unticked box — the merge gate's AC check saw to that.

**The best AC work in the window was a criterion being argued DOWN rather than up.** #458's guard
was originally described as asserting cross-project uniqueness. The reviewer's round-2 finding was
that the guard "asserts something structurally unable to fire"; the resolution was to *rename the
check to what it actually asserts* (per-project prefix conformance) after measuring the real input
— 46/46 `SF:` lines prefixed, 0 doubly prefixed, 46/46 resolving on disk — rather than strengthen
it into a new failure mode. Naming a check honestly is a legitimate answer to "this check is
weaker than its name"; it is also the answer that is easiest to fake, which is why the 46/46
measurement is the load-bearing part.

Both are the same instruction: **when you fix a finding, re-run the measurement that found it
against the fix** — not against the code you meant to write.

## 4. Review actions — the window that stopped reviewing itself

**The single largest behavioural change in the series: non-independent verdicts fell from 100% to
8%.**

| Provenance | Verdicts | Where |
|---|---|---|
| Independent `pr-reviewer`, stated | **21 of 26** | #449 ×3, #450 r2, #451 ×2, #452 ×5, #455 ×2, #458 ×4, #462, #463 ×3 |
| NOT independent, **disclosed** | **2 of 26** | #448 r1, #449 r1 — both name the solo directive in their own paragraph |
| **No provenance statement either way** | **3 of 26** | #450 r1, #464 r1, #464 r2 |

The window opens solo (the owner's standing directive from v1.15.x) and switches to dispatched
`pr-reviewer` subagents from #449's second verdict onward. Both solo verdicts disclose, so the
rule-13 disclosure clause holds **where it applies**. But three verdicts state nothing at all, and
that is a measurement problem the column cannot survive: the disclosure rule only obliges a
*non-independent* verdict to speak, so silence is ambiguous — it reads identically to an
independent review that did not bother. **The denominator for this row is 23, not 26.** §6 change
D fixes the rule rather than the row.

**What the reviewers caught that the authors missed** — the pattern across all 10 threads is one
sentence: *the reviewer re-ran the measurement instead of reading the fix report.* Verbatim from
the window: "I re-measured the two blockers rather than reading the fix report" (#450 r2), "I
re-derived each one rather than accepting the report" (#451 r2), "I verified each rather than
accepting the report" (#463 r2), "Re-measured independently at `1256efaf`" (#462). Two of those
re-measurements found the fix incomplete.

**#463's reviewer refused to reuse a number that was still true.** Round 2's suite figures could
have been carried into round 3; instead they were re-measured, because #458 had landed in the same
Vitest project between the rounds. Nothing was wrong with the old number — the point is that its
*basis* had moved, and a figure whose basis moved is a claim, not a measurement.

**Two delta-confirms on #463 were forced by rebases**, and #452 needed one after a 1-commit drift.
That is the approval-covers-head gate working as designed: 0 merges on a stale approval, across 10
PRs and 26 verdicts, for the fifth consecutive release.

**#464's round 1 is the most instructive verdict in the window**, because it REQUESTED CHANGES on
a claim the project itself had written down a day earlier (§3, class F #9). A reviewer contradicting
the repo's own committed lesson — by running the lint's seam rather than quoting the lesson — is the
behaviour that keeps a knowledge base from calcifying.

## 6. The changes

**A — `scripts/verdict-heading-lib.sh`: ONE verdict-heading grammar, replacing three drifted
copies.** *(hook > skill > charter: this is the hook tier.)*

The evidence is #458, and it is a live false-ALLOW in this window. The author posted:

> Round-3 delta — head is now `89e05b78`. The round-3 APPROVE covered `70a8cfb4`; two things moved
> since, so it needs a delta-confirm rather than standing.

All three verdict readers — `pre-merge-gate.sh`, `audit_no_verdict_merges.sh`, `retro_metrics.sh` —
tested for a marker **anywhere in the first line**, so that sentence became "the newest verdict".
Its first marker reads APPROVE, and it post-dates the head, so it satisfied check 1 (rule 13) *and*
check 1b (approval-covers-head). **Between 00:08:23Z and the real round-4 APPROVE at 00:22:36Z, the
gate would have merged on a sentence asking it not to.** Nothing bad happened — the real verdict
arrived first — which is exactly why it had to be found by measurement rather than by an incident.

What the old code said about this residual is the second half of the lesson. It was documented, and
it argued that **no lexical rule could separate** an author's note from a real heading that puts
prose before the marker (`## Round 3 — ✅ APPROVED`, `PR-REVIEWER VERDICT: APPROVE`). That was an
assertion. Measured over **229 merged PRs / 361 marker-bearing first lines**: whitelist those two
prefixes, require the line to *begin* with the marker, and require a non-hyphen boundary after it,
and **354 are accepted, 7 rejected, and all 7 rejections are correct** (6 author notes + #83's July
blockquote verdict). Exactly **one** classification anywhere in the repo's history changes, and it
is #83, 2026-07-26, outside every window the audit runs on.

Replaying the gate at the instant each of the 6 author notes landed: **3 flip ALLOW → DENY**
(#181, #281, #458). The other three were already denied for other reasons.

- The grammar lives in one file with a mutation contract (**19 real headings, 9/0/0 mutants**), and
  it names every case's PR so no case is invented.
- One mutant exists only because the first implementation shipped the defect this retro is about:
  the boundary was written `(?![A-Za-z0-9-])`, which **passed every self-test under `jq`** and died
  at runtime under `gh -q` — gojq is Go's RE2 and has no lookahead. The suite cannot reach gojq
  offline, so it pins the input instead (no `(?!`, `(?<`, backreferences).
- Wired: `pre-merge-gate.test.sh` gains 7 cases (4 fail against the old gate, verified) and its
  contract goes **23 → 24**; `audit_no_verdict_merges.test.sh` gains 2 cases (both fail against the
  old detector, verified) and its contract **18 → 19**; `retro_metrics.sh` also gains the
  trusted-association filter the other two always had (measured: a no-op on all 229 merged PRs) and
  now prints `non-verdict bodies skipped: N`.
- **The rule-13 audit was re-measured in both directions, not reasoned about.** Running the
  pre-change script (`git show HEAD:scripts/audit_no_verdict_merges.sh`) and the tightened one over
  `--since 2026-08-15 --limit 200` returns an **identical PR-by-PR classification** — the same ten
  entries in the same order with the same `NO-VERDICT`/`UNAPPROVED` shapes (the only diff is the
  ledger annotation, which the temp-dir copy cannot resolve a path to). On the window CI actually
  runs, `--since 2026-09-14T00:00:00Z --limit 400` exits **0**: *56 merged PR(s) — 49 gated by a
  pre-merge verdict, 7 acknowledged*. So the tightening adds no alarm anywhere the detector runs;
  #355, #321 and #261 are pre-existing entries **outside** the scheduled window under BOTH scripts.
- **Comparability measured, not assumed.** Re-running the instrument on three already-published
  windows reproduces every cell with `0 skipped`: v1.15.0 (`v1.14.3 436` → 6 PRs / 11 / 1.83 / 50% /
  45%), v1.15.1 (`436 441` → 6 / 6 / 1.00 / 100% / 0%), v1.15.2 (`441 446` → 3 / 3 / 1.00 / 100% /
  0%). Only v1.16.0's own row moves, by one verdict.

**B — lessons §43 rewritten: the residual is closed, and the meta-lesson is why it stayed open.**
The old revisit trigger was *"the first fix report with a leading marker posted while the standing
verdict is NEGATIVE"* — check 1's failure mode. Check 1b was added to the **same selection** one
release later, and against check 1b the dangerous standing verdict is a **positive** one that no
longer covers the head. The trigger could not fire on the case that mattered. **A revisit trigger
written for one consumer of a shared selection does not migrate when a second consumer joins it** —
prefer a case that fails to a condition somebody has to remember.

**C — charters: `pr-reviewer.md` + `PLAYBOOK.md`.** The verdict heading must *state* the marker, not
mention it, with the accepted forms named; and — new — **every verdict states its provenance in one
line, in both directions**. Rule 13 only obliges a non-independent verdict to disclose, which makes
silence ambiguous: this window's 3 silent verdicts are indistinguishable from independent reviews
that did not bother, and they shrink the trend column's denominator from 26 to 23.

**D — `release-retro` skill.** Count verdicts with the shared grammar, quote the instrument's
`non-verdict bodies skipped` line, and do **not** re-derive rows published under the older filter.

**E — `release-manager.md` step 11.** Reconcile the board against the issues the tag actually
closed, queried from git rather than from the release label — because the label queue reports
`empty (checked)` for an issue that was never labelled, which is precisely how #461, #447, #459 and
#460 passed the existing gate (§2). The rule-11 shape (an issue opened and closed inside one PR)
is explicitly exempt.

**F — the two residuals this retro was handed, fixed rather than filed.**
- lessons §81 closed with "The cost is a **deferral**, which is cheap" — a round-1 leftover that its
  own rewritten body supersedes. Under construction C nothing is deferred; the cost is **one errata
  line**. The polarity argument it supports (do NOT loosen the lint) is unchanged.
- The `## [1.16.0]` CHANGELOG entry called the lcov guard "per-project resolvability" and said
  "resolvability fails it". Both overstate what it asserts. **The in-place edit §81 says is illegal
  on `[Unreleased]` is legal here** — the text has rotated into a released section, and check 4 is
  set semantics over `[Unreleased]` only. Corrected in place, the appended errata paragraph removed,
  and verified: `scripts/check_changelog_merge.sh` → `ok: merged CHANGELOG passes all 4 checks`.
  This is §81's own construction "D/optional housekeeping" being exercised for the first time.

**Considered and NOT changed, with reasons** (the `release-retro` skill's rule: a retro that
changes nothing must say why — and so must a finding that produces no change):
- **The CI-topology masking residual** (`pr-evidence-e2e.yml`). #463's reviewer asked for the
  acceptance comment to admit it can mask a **failing** run, not just a passing one. **That landed
  in-window** (`:41-53`); there is nothing left to write. The topology fix itself still costs a
  `workflow_dispatch` relay for an on-demand tier whose normal state is `skipped` — unchanged
  judgement, now with the honest downside written down.
- **A lint for class F on documentation surfaces.** Four of nine class-F findings are in docs, and
  the temptation is a checker. There is no mechanical oracle for "this sentence was measured"; the
  instrument that DID move this class is `retro_metrics.sh` (figures produced rather than typed),
  and change A extends it. A lint here would be a check that cannot fail — class G, written by the
  retrospective that counts class G.
- **`round-1 approvals` is not redefined.** #449 is counted as a round-1 approval and took four
  verdicts. The definition ("the first verdict was an APPROVE") has been carried since v1.12.0 and
  silently changing it would break every row above. §8 names it instead.

## 8. Prediction for the next release

Clauses 1, 3, 5 and 6 are **holding** and stay as written in [v1.15.1 §8](v1.15.1.md) — do not
restate them here, score them there. The changes this window's evidence justifies:

1. **Clause 2 (class F) is kept at ≤4 blocker+major and ≤2 on doc surfaces, and the control
   changes.** Re-measuring one sentence from the previous retro passed while the class scored 9,
   so the control is too easy. Replace it: **re-measure the load-bearing sentence of the previous
   retro's LARGEST change** — for the next window that is change A's claim that the tightened
   grammar reproduces every published row. Run the three oracles; if any cell moves, the change
   broke the series and the retro says so in the table, not in a footnote.
2. **Clause 4 becomes: 100% of verdicts state provenance, in either direction.** The current clause
   can pass at 2 of 2 while 3 of 26 say nothing. Scored from the verdict bodies, denominator = all
   canonical verdicts.
3. **Clause 7 keeps its wording and gains its falsifier:** the security check must be *posted on
   the release PR before `mergedAt`*. #464 ran it and passed it — after the merge. Score it from
   the thread's timestamps, never from the alert counts.
4. **Clause 8 narrows:** every issue a release closes is a Project 3 item, **in that release's
   bucket**, carrying its `release:vX.Y.Z` label — *except* an issue opened and closed inside a
   single PR (the rule-11 shape, #461), which is exempt and must be named as such. The bucket half
   is new and it failed twice this window (#67, #339).
5. **NEW — the merge gate denies at least one merge on the tightened grammar, or nobody notices it
   at all.** This is the observable for change A. Either outcome is informative: a deny means the
   shape recurred and is now caught; zero denies with zero complaints means the charter change (C)
   is carrying it. A **false** deny — a real reviewer verdict rejected as non-canonical — is the
   failure mode to watch for, and it should appear as a "repost the heading" round. If one occurs,
   report the heading verbatim; the grammar's prefix whitelist is derived from 361 real headings
   and a miss means it needs a 362nd.
6. **NEW — mean rounds ≥2.0 with class F and G both falling.** This window's 2.60 is not a
   regression from 1.00 on a 3-PR corpus; it is the first honest number since v1.14.3. The thing
   to watch is whether the *content* of those rounds shifts from "the claim was not measured" to
   material difficulty. If rounds stay high while F and G fall, the constraint has moved and the
   answer is not another charter paragraph (v1.15.1 falsifier (e), still standing).

**Falsifiers.** (a) Clauses 1, 3 and 5 go to "pass" for free on a small corpus — state the corpus

only denies visible in a PR thread or the bypass log. (c) Clause 1's control is only meaningful if
the oracles are run at the *tightened* grammar's head; running them against the old script proves
nothing. (d) Every clause above is scored from measurement in the next retrospective's §7 table,
with the command that produced it — a clause scored from memory is the class-F defect this series
